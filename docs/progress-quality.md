## 1) استيراد المحتوى
**المسار:** لوحة التحكم ← المنشورات ← زر «استيراد» (`/admin/posts/import`).
- **الملف:** JSON (قائمة، أو `{"posts": [...]}`) أو CSV. الترميز UTF-8، ويُقبل BOM الذي يضيفه Excel. الحد 500 صف و5 ميغابايت.
- **الأعمدة الإلزامية:** `category` و`title_ar` و`content_ar`.
- **الأعمدة الاختيارية:** `id` و`topic` و`content_en` و`tags` و`external_ref` و`section_slug` و`title_en` و`summary_ar` و`source_name` و`content_type` و`file_url`.
- **الوسوم:** قائمة في JSON. وفي CSV مفصولة بـ `|` (ويُقبل أيضاً `،` و`;` و`,`).
- **المعاينة قبل الحفظ:** جدول بكل الصفوف (العنوان والرابط المختصر، والمسار والقسم، والنوع، واللغة)، ومعها:
  - **أخطاء** كل صف بالعربية: حقل ناقص، قسم غير موجود، قسم من مسار آخر، slug مكرر في القاعدة أو في نفس الملف، مسار أو نوع غير معروف، رابط لا يبدأ بـ http.
  - **تحذيرات** لا تمنع الاستيراد: عمود غير معروف، قسم موقوف، أو قسم اختير تلقائياً.
  - فلتر «الكل / الصالحة / فيها أخطاء». وعلى الجوال يتحول الجدول إلى بطاقات.
- **الحالة بعد الاستيراد:** «مسودة» أو «قيد المراجعة» فقط، ويرفض الـ API قيمة `published` (422). يُستورد الصالح فقط بعد نافذة تأكيد، ثم روابط للمنشورات وللمراجعة. **لا فهرسة إلا عند النشر.**
- **القرارات:**
  - `id` يصير الرابط المختصر (slug) إن كان بحروف إنجليزية. والرقم وحده يصير `post-12`.
  - بلا `section_slug` تُوضع المادة في أول قسم رئيسي مفعّل من المسار (مع تحذير).
  - **النص يُحفظ حرفياً.** الاستثناء الوحيد شكلي: نص عادي بلا وسوم HTML تُلفّ فقراته (المفصولة بسطر فارغ) في `<p>` مع تهريب الرموز `< > &`، حتى يظهر فقرات كما في المحرر. لا يتغير أي حرف، والاختبار يتحقق من ذلك.
- **القوالب:**
  - زرّا «قالب JSON فارغ» و«قالب CSV فارغ» في الصفحة نفسها، يُولَّدان في المتصفح.
  - رابط «مثال معبأ بصف واحد» يفتح `docs/content-template.json` و`docs/content-template.csv`. نسختهما في `frontend/public/templates/`، والنص فيهما توضيحي غير شرعي.
- **الـ Backend:** `POST /api/admin/posts/import` بالجسم `{format, content, status, dry_run}`. الاختبار: `import_test.py` (35 فحصاً).

## 2) توحيد النص العربي (`backend/app/rag/normalize.py`)
- **`normalize_ar`:**
  - أ إ آ ٱ ← ا، و ى ← ي، و ة ← ه.
  - حذف التشكيل (ومعه علامات المصحف والألف الخنجرية) والتطويل.
  - NFKC لأشكال العرض، فمثلاً «ﷲ» تصير «الله».
  - توحيد المسافات.
- **أين يُطبَّق:** على السؤال (`embed_query`) وعلى نص كل مقطع قبل التضمين (`index_post`) فقط. **`chunk_text` المحفوظ، والنص المعروض من posts، لا يتغيران**، ويتحقق `rag_test` من ذلك.
- **إعادة الفهرسة:** شغّلتُ `POST /api/admin/ai/reindex`، لكن القاعدة كانت بلا منشورات، فالنتيجة 0. ستُفهرس المواد الحقيقية بالتوحيد تلقائياً عند نشرها. وإن كانت عندك مواد منشورة قبل هذا التحديث فاضغط «إعادة بناء الفهرس» في «قاعدة المعرفة».

## 3) البحث الهجين
- **SQL** (في `schema.sql`، آمن للتكرار):
  - `CREATE EXTENSION pg_trgm`.
  - الدالة `daiah_normalize_ar` (نفس قواعد بايثون).
  - عمود محسوب `post_chunks.search_text` مع فهرس GIN trigram.
  - الدالة `match_post_chunks_hybrid`: ترجع أفضل N مقطعاً دلالياً + أفضل N نصياً (`word_similarity` ≥ 0.2) مع رتبة كل مقطع.
- **الدمج:** بـ Reciprocal Rank Fusion (k=60) على مستوى المنشور في `search.py`.
- **العتبة:** تبقى على التشابه الدلالي. المادة المعروضة هي أول نتيجة بترتيب الدمج تشابهها الدلالي ≥ العتبة، وإلا fallback.
- **الأمان:** إذا لم تُنفَّذ الدالة أو حدث فيها أي خطأ، يرجع البحث **تلقائياً للدلالي**، فلا يتعطل المساعد. ويعيد المحاولة كل 10 دقائق. ويمكن فرض الدلالي بـ `SEARCH_MODE=semantic`.
- **التحقق على Supabase الحقيقي:** نُفِّذ `schema.sql`، وقِيست الدالة الحقيقية `match_post_chunks_hybrid` بـ `rag_test.py --eval-only` (وضع `hybrid`).
  نتائجها **مطابقة تماماً للمحاكاة** (`hybrid_sim`) في كل المقاييس، وأسرع (1538 ms للسؤال مقابل 3347 ms للدلالي في هذا التشغيل، لأن الدالة ترجع الدلالي والنصي في رحلة واحدة).

## أوامر SQL المطلوبة منك
**الصق `backend/db/schema.sql` كاملاً في Supabase SQL Editor ثم Run.** هو آمن للتكرار، والإضافات الجديدة كلها في قسم «البحث الهجين» قبل آخر سطر:
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE OR REPLACE FUNCTION daiah_normalize_ar(t text) ...          -- IMMUTABLE
ALTER TABLE post_chunks ADD COLUMN IF NOT EXISTS search_text TEXT
    GENERATED ALWAYS AS (daiah_normalize_ar(chunk_text)) STORED;   -- يُملأ تلقائياً للصفوف الموجودة
CREATE INDEX IF NOT EXISTS ix_post_chunks_search_trgm ON post_chunks USING gin (search_text gin_trgm_ops);
CREATE OR REPLACE FUNCTION match_post_chunks_hybrid(...)            -- + REVOKE/GRANT لـ service_role فقط
NOTIFY pgrst, 'reload schema';
```

**بعد التنفيذ:**
1. شغّل `cd backend ; .venv\Scripts\python.exe rag_test.py --eval-only`. يجب أن يظهر وضع `hybrid` (الدالة الحقيقية) بجانب `hybrid_sim`. إن ظهر تحذير «غير موجودة» فالـ SQL لم يُنفَّذ.
2. لا حاجة لإعادة الفهرسة من أجل `search_text`، فهو عمود محسوب.

**إن فشل أي سطر:** الـ Backend يستمر بالبحث الدلالي تلقائياً، فلا يتأثر المساعد. أرسل لي رسالة الخطأ.

## مشكلات وملاحظات متبقية
1. ~~دالة SQL الهجينة لم تُختبر على Postgres حقيقي~~ **حُلّت:** نُفِّذ `schema.sql` واختُبرت الدالة على Supabase، وأرقامها مطابقة للمحاكاة (القسم 3).
2. **مجموعة التقييم صغيرة ومحايدة** (5 مواد). الأرقام تُظهر الاتجاه، لكن المعايرة الحقيقية (العتبة و`TEXT_MIN = 0.2`) يجب أن تُعاد على المحتوى الحقيقي.
3. **أداء الجوال في Lighthouse** بين 79 و88 (وسيط) في 4 صفحات، والكمبيوتر 96–100. الأسباب والحدود في البند 7.
4. **CLS متقطع في صفحة المادة على الكمبيوتر** (0.12 في تشغيل، و0 في آخر): سببه تبديل الخط (Tajawal) على النص المرسوم من الخادم. الحل الجذري `font-display: optional`، لكنه قد يُظهر خط النظام في أول زيارة بطيئة، فتركته `swap` حفاظاً على الهوية.
5. **الكاش في ذاكرة العملية:** كافٍ لنسخة واحدة على Render. ومع عدة نسخ، قد يتأخر ظهور تعديل حتى 60 ث في النسخ الأخرى، و15 ث للإعدادات.
6. **قياس الزمن من هذا الجهاز** يتأثر بشبكة Supabase البعيدة (~400 ms للرحلة)، وبحالة Gemini (ظهرت 429/503/504 أثناء القياس). الأرقام للمقارنة، لا للإنتاج.
7. **إصلاح جانبي:** `e2e_run.py` كان ينهار عند توجيه مخراته إلى ملف (ترميز cp1256 مع الرمز التعبيري)، فأصلحته. وفي `rag_test.py` صار التقييم يجري قبل تعديل المواد وإلغاء نشرها.
8. **البيانات التجريبية:** كل ما أنشأته حُذف (أقسام، منشورات، سجلات محادثة للرسم والمساعد). ولم أنشئ مراكز.
